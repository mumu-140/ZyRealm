# P0.3 Live Request State + Manual Interrupt — Design

> Status: design locked for review
> Baseline: `main@8c629cddb1b41e28322950736b8089d6c19a6dcf`
> Branch: `codex/p0.3-live-request-interrupt`
> Date: 2026-09-15

## 1. Goal

P0.3 adds a small request-control plane for requests that are currently executing through the relay.

The feature has two user-visible outcomes:

1. the admin UI can inspect active relay requests before their durable `RelayLog` exists;
2. an administrator can manually interrupt one active request without turning the interrupt into provider failover, circuit-breaker evidence, or a WebSocket connection shutdown.

This is **not** a new logging subsystem and **not** a new failover strategy.

## 2. Source audit conclusions

The implementation is constrained by the current `main` source rather than earlier roadmap assumptions.

### 2.1 Durable logs are completion records

`RelayLogAdd` assigns the durable log ID and notifies log subscribers when the relay log is added after request processing. Existing log SSE therefore represents completed log events, not in-flight request state.

P0.3 must not use `RelayLog.ID` as the active-request identity and must not change the relay log persistence lifecycle merely to expose live state.

### 2.2 Cancellation provenance already has important semantics

Current cancellation code and tests distinguish:

- downstream/client cancellation;
- ambiguous upstream/transport cancellation while the outer request is still alive;
- first-token timeout;
- local exact-replay budget exhaustion.

Manual interrupt must be a new explicit cancellation cause. It must not be inferred from generic `context.Canceled` and must not be classified as downstream/client cancellation.

### 2.3 Retry and protocol fallback share a request-level context

HTTP same-channel retry and protocol-fallback paths currently consume the same outer request context. First-token timeout is the existing precedent for a cause-bearing child context.

P0.3 therefore introduces one request/round execution context which is shared by all attempts belonging to that logical request.

### 2.4 Downstream WebSocket context is connection-scoped

`HandleWSResponse` creates a connection-level context with a maximum age and processes multiple `response.create` messages on that same connection.

Manual interrupt must never cancel that connection-level context. Each `response.create` requires its own round-scoped child context so that interrupting one round leaves the downstream WebSocket alive for a later `response.create`.

### 2.5 Dispatch state already encodes replay risk

Current routing uses dispatch state and downstream commitment to derive replay safety. In particular, a cancellation after `MAYBE_SENT` can have an unknown upstream outcome.

A manual interrupt is therefore terminal for the current logical request. It must not automatically continue to another protocol, credential, or provider.

## 3. Hard invariants

The implementation must preserve all of the following:

1. **No database migration.** Live request state is ephemeral process state.
2. **No credential leakage.** Never expose API-key secret values, channel credentials, Authorization headers, raw request bodies, or raw response bodies.
3. **No automatic failover after manual interrupt.** Manual intent is terminal for the logical request.
4. **No health pollution.** Manual interrupt must not create provider cooldown, credential cooldown, circuit-breaker failure, model-suspect state, or outlier failure evidence.
5. **No WebSocket connection kill.** Interrupting a `response.create` round must not terminate the downstream WebSocket connection.
6. **No semantic collapse of existing cancellation causes.** Client cancellation, ambiguous transport cancellation, first-token timeout, and local replay budget keep their existing behavior.
7. **No live/durable lifecycle mixing.** Active request state and completed `RelayLog` data use separate types, APIs, and frontend query keys.
8. **Single-instance semantics are explicit.** P0.3 coordinates requests inside the current process only. Multi-replica cancellation is deferred until deployment actually requires shared coordination.

## 4. Runtime architecture

### 4.1 Request control object

Each logical HTTP request or WebSocket `response.create` round gets one shared request-control object.

Conceptually it owns:

- a generated `live_request_id` independent of `RelayLog.ID`;
- the execution context derived from the natural parent request/round context;
- a `context.CancelCauseFunc`;
- mutable live metadata guarded for concurrent access;
- the explicit manual-interrupt flag/cause.

Attempt clones share a pointer to this object. They do not clone cancellation ownership or create separate logical request IDs.

### 4.2 Process-local registry

A process-local registry owns active control objects by `live_request_id`.

Required operations:

- register at logical request start;
- snapshot all active requests;
- update safe live metadata during routing/attempt execution;
- interrupt one request by ID;
- unregister exactly once when the logical request finishes for any reason.

The registry stores only active requests. Completion history remains the responsibility of the existing `RelayLog` path.

### 4.3 Lifecycle

The intended lifecycle is:

```text
ingress
  -> create request/round control
  -> register active request
  -> routing
  -> attempt(s)
  -> natural completion | manual interrupt | client cancel | other terminal result
  -> durable RelayLog follows existing behavior
  -> unregister active request
```

Cleanup is guaranteed with `defer` at the logical request/round owner, not scattered across individual attempt exits.

## 5. Live snapshot contract

P0.3 exposes only operational metadata needed to understand the currently executing request.

Minimum snapshot fields:

- `request_id`
- `started_at`
- `transport` (`http` or `websocket`)
- `api_key_id`
- `requested_model`
- `channel_id`
- `channel_key_id`
- `ingress_protocol`
- `upstream_protocol`
- `provider_attempt`
- `wire_attempt`
- `dispatch_state`
- `downstream_committed`
- `phase`
- `interrupt_requested`

Allowed coarse phases:

- `routing`
- `attempting`
- `streaming`
- `interrupting`

P0.3 does not expose raw prompt text, raw response text, secrets, headers, or credentials.

An attempt which has not completed must not be assigned a fabricated `RoutingDecision`. Completed attempt decisions remain part of existing audit/log structures.

## 6. Manual interrupt semantics

### 6.1 Explicit cause

Manual interrupt uses a dedicated cause (conceptually `errManualInterrupt`) through `context.WithCancelCause` / `CancelCauseFunc`.

Classification must recognize this cause before generic client-cancel or ambiguous-transport handling.

### 6.2 Routing decision

A manual interrupt is health-neutral and terminal:

- `rule_id = manual_interrupt`
- `failure_scope = request`
- `directive = terminal`
- `terminal = true`
- `runtime_effect = none`
- `circuit_effect = none`
- `outlier_scope = ignore`
- no retry on same credential
- no credential rotation
- no protocol fallback
- no provider failover

### 6.3 Replay safety remains orthogonal

Manual interrupt is **not** a replay-safety value.

Replay safety continues to be derived from the already-known delivery state:

- pre-dispatch -> `not_sent`;
- `MAYBE_SENT` without downstream commitment -> `unknown_upstream_outcome`;
- downstream payload committed -> `downstream_committed`.

This preserves the distinction between **why execution stopped** and **whether replay is safe**.

## 7. HTTP behavior

For normal HTTP ingress, the request-control execution context is a child of the existing request context.

Manual interrupt cancels that child context only. The transport observes cancellation and the routing layer classifies the cause as `manual_interrupt`.

If downstream output has not been committed, the relay may return a stable interruption error response according to the existing response-writing constraints. If downstream output is already committed, no second response envelope is written.

Regardless of response shape, manual interrupt is terminal and health-neutral.

## 8. WebSocket behavior

The downstream WebSocket connection keeps its existing connection-level context.

For each `response.create`:

1. derive a new round context from the connection context;
2. create/register one request-control object using that round context;
3. run routing and all attempts with that round context;
4. on manual interrupt, cancel only that round context;
5. finalize/unregister the round;
6. return to the WebSocket message loop with the connection still alive.

The critical regression invariant is:

```text
response.create #1 -> manual interrupt -> round #1 stops
same downstream WS remains open
response.create #2 -> can execute normally
```

Connection shutdown, normal client disconnect, and the existing 60-minute connection age remain connection-level concerns and are not redefined by P0.3.

## 9. Admin API

P0.3 adds a dedicated authenticated admin API namespace rather than extending `/api/v1/log` payloads.

Proposed contract:

- `GET /api/v1/live-request/list`
  - protected by `middleware.Auth()`;
  - returns current live snapshots only;
  - order is deterministic, newest first or start-time order documented by implementation.

- `POST /api/v1/live-request/:id/interrupt`
  - protected by `middleware.Auth()`;
  - requests manual interruption of the active logical request;
  - success if the request is still registered, including repeated interruption while it remains in the registry;
  - `404` when the request is no longer active or the ID never existed.

The admin endpoint never accepts or returns credential secrets.

## 10. Frontend behavior

The first P0.3 UI uses a separate active-request query with short polling rather than overloading completed-log SSE.

Recommended MVP:

- React Query `GET /api/v1/live-request/list` every approximately 1 second while the log page is mounted;
- a compact **Active requests** region above durable logs;
- each active row/card shows safe operational metadata and an interrupt action;
- interrupt mutation immediately marks the row as interrupting/disabled locally, then refreshes the active query;
- durable logs continue to use the existing log query/SSE path unchanged.

A later typed live-state SSE can replace polling without changing the registry or API semantics if sub-second updates become worthwhile.

## 11. TDD and acceptance gates

Production code is not written until the corresponding behavior has a failing test.

### 11.1 Registry/control tests

Must prove:

- registration appears in snapshots;
- unregister removes the request;
- snapshot data is copied safely rather than exposing mutable internals;
- interrupt is idempotent while registered;
- unknown IDs are rejected;
- the manual cause reaches the child execution context;
- parent context is not canceled by manual interrupt.

### 11.2 Routing semantics tests

Must prove:

- manual interrupt is `terminal`;
- health/runtime/circuit effects are all neutral;
- pre-dispatch replay safety is `not_sent`;
- post-dispatch replay safety is `unknown_upstream_outcome`;
- committed delivery remains `downstream_committed`;
- no retry/fallback/provider rotation occurs after manual interrupt.

### 11.3 HTTP integration tests

Must prove at minimum:

- pre-dispatch interrupt produces zero upstream request hits;
- an in-flight post-dispatch interrupt ends the logical request without trying another provider;
- manual interrupt does not record a health failure;
- active registry cleanup occurs on success, error, client cancellation, and manual interrupt.

### 11.4 WebSocket regression tests

Must prove:

- the live registry contains the current `response.create` round;
- interrupting that round ends only that round;
- the downstream WebSocket connection remains usable;
- a subsequent `response.create` on the same downstream connection can run;
- connection-level cancellation still terminates the session normally.

### 11.5 Existing regressions

Existing cancellation and routing tests remain green, especially those covering:

- client cancellation provenance;
- ambiguous transport cancellation;
- first-token timeout;
- exact replay local budget;
- dispatch state and replay safety;
- downstream commitment.

### 11.6 Frontend tests

Must cover the active-request presentation/state reducer or component behavior used for:

- rendering active snapshots;
- disabling repeated interrupt clicks once interruption is requested;
- removing a request after it disappears from the next snapshot.

## 12. Out of scope for P0.3

The following are explicitly deferred:

- database persistence of live state;
- distributed/multi-replica interrupt coordination;
- Redis or another shared cancellation bus;
- replacing completed-log SSE;
- sub-second live-state SSE;
- interrupt-all / bulk interrupt;
- automatic retry or failover after manual interrupt;
- changing provider health heuristics for ordinary failures;
- redesigning the durable log schema;
- exposing request/response content in the live-state API.

## 13. Implementation sequence after design approval

The implementation plan will decompose this design into small RED -> GREEN steps:

1. registry/control contract;
2. manual-interrupt classification and health neutrality;
3. HTTP request lifecycle integration + admin API;
4. WebSocket round-scoped integration;
5. frontend active-request panel + interrupt mutation;
6. full CI, source-audit/roadmap documentation, and merge gate.

No production deployment is part of P0.3 implementation or merge verification.
